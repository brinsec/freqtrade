    开发帮助¶

    本页面向 Freqtrade 的开发人员、想要为 Freqtrade 代码库或文档做出贡献的人员，或想要了解他们正在运行的应用程序的源代码的人员。

    欢迎所有贡献、错误报告、错误修复、文档改进、增强和想法。我们在 GitHub 上跟踪问题，并在 discord 上有一个开发频道，您可以在那里提问。

    文档¶

    文档可在 https://freqtrade.io 获得，需要随每个新功能 PR 一起提供。

    文档的特殊字段（如注释框等）可以在这里找到。

    要在本地测试文档，请使用以下命令。

    pip install -r docs/requirements-docs.txt
mkdocs serve

    这将启动一个本地服务器（通常在端口 8000 上），因此您可以看到一切是否符合您的要求。

    开发者设置¶

    要配置开发环境，您可以使用提供的 DevContainer，或使用 setup.sh 脚本并在询问"您想安装开发依赖项 [y/N]？"时回答"y"。 或者（例如，如果您的系统不受 setup.sh 脚本支持），请遵循手动安装过程并运行 pip3 install -r requirements-dev.txt - 然后是 pip3 install -e .[all]。

    这将安装开发所需的所有工具，包括 pytest、ruff、mypy 和 coveralls。

    然后通过运行 pre-commit install 安装 git hook 脚本，这样您的更改将在提交前在本地进行验证。 这已经避免了很多等待 CI 的时间，因为一些基本的格式检查是在您的机器上本地完成的。

    在打开拉取请求之前，请熟悉我们的贡献指南。

    Devcontainer 设置¶

    最快、最简单的入门方法是使用带有 Remote container 扩展的 VSCode。 这使开发人员能够在不需要在本地计算机上安装任何 freqtrade 特定依赖项的情况下启动具有所有必需依赖项的机器人。

    Devcontainer 依赖项¶

    • VSCode
    • docker
    • Remote container 扩展文档

    有关 Remote container 扩展 的更多信息，最好查阅文档。

    测试¶

    新代码应包含基本单元测试。根据功能的复杂性，审阅者可能会要求更深入的单元测试。 如有必要，Freqtrade 团队可以提供帮助并提供编写良好测试的指导（但请不要期望有人为您编写测试）。

    如何运行测试¶

    在根文件夹中使用 pytest 运行所有可用的测试用例并确认您的本地环境设置正确

    功能分支

    测试应在 develop 和 stable 分支上通过。其他分支可能正在进行中，测试尚未正常工作。

    检查测试中的日志内容¶

    Freqtrade 使用 2 种主要方法来检查测试中的日志内容：log_has() 和 log_has_re()（使用正则表达式检查，用于动态日志消息）。 这些可从 conftest.py 获得，并且可以在任何测试模块中导入。

    检查示例如下所示：

    from tests.conftest import log_has, log_has_re

def test_method_to_test(caplog):
    method_to_test()

    assert log_has("This event happened", caplog)
    # Check regex with trailing number ...
    assert log_has_re(r"This dynamic event happened and produced \d+", caplog)

    调试配置¶

    要调试 freqtrade，我们建议使用 VSCode（带有 Python 扩展）和以下启动配置（位于 .vscode/launch.json）。 详细信息显然会因设置而异——但这应该可以让您开始。

    {
    "name": "freqtrade trade",
    "type": "debugpy",
    "request": "launch",
    "module": "freqtrade",
    "console": "integratedTerminal",
    "args": [
        "trade",
        // Optional:
        // "--userdir", "user_data",
        "--strategy", 
        "MyAwesomeStrategy",
    ]
},

    命令行参数可以添加到 "args" 数组中。 此方法也可以用于调试策略，通过在策略内设置断点。

    类似的设置也可以用于 Pycharm——使用 freqtrade 作为模块名称，并将命令行参数设置为"参数"。

    正确使用 venv

    使用虚拟环境（您应该使用）时，请确保您的编辑器使用正确的虚拟环境以避免问题或"未知导入"错误。

    Vscode¶

    您可以在 VSCode 中使用命令"Python: Select Interpreter"选择正确的环境——这将显示扩展检测到的环境。 如果您的环境未被检测到，您也可以手动选择路径。

    Pycharm¶

    在 pycharm 中，您可以在"Run/Debug Configurations"窗口中选择适当的环境。

    启动目录

    这假设您已检出仓库，并且编辑器在仓库根级别启动（因此 pyproject.toml 位于仓库的顶级）。

    错误处理¶

    Freqtrade 异常都继承自 FreqtradeException。 然而，不应该直接使用这个通用错误类。相反，存在多个专门的子异常。

    以下是异常继承层次结构的概述：

    + FreqtradeException
|
+---+ OperationalException
|   |
|   +---+ ConfigurationError
|
+---+ DependencyException
|   |
|   +---+ PricingError
|   |
|   +---+ ExchangeError
|       |
|       +---+ TemporaryError
|       |
|       +---+ DDosProtection
|       |
|       +---+ InvalidOrderException
|           |
|           +---+ RetryableOrderError
|           |
|           +---+ InsufficientFundsError
|
+---+ StrategyError

    插件¶

    Pairlists¶

    您有一个很棒的新交易对选择算法想法想要试用？太好了。 希望您也愿意将其贡献回上游。

    无论您的动机是什么——这应该能让您开始尝试开发新的 Pairlist Handler。

    首先，查看 VolumePairList Handler，并最好将其复制为新的 Pairlist Handler 的名称。

    这是一个简单的 Handler，它作为如何开始开发的好例子。

    接下来，修改 Handler 的类名（理想情况下与模块文件名对齐）。

    基类提供交易所实例（self._exchange）、pairlist 管理器（self._pairlistmanager）、主配置（self._config）、pairlist 专用配置（self._pairlistconfig）以及在 pairlist 列表中的绝对位置。

            self._exchange = exchange
        self._pairlistmanager = pairlistmanager
        self._config = config
        self._pairlistconfig = pairlistconfig
        self._pairlist_pos = pairlist_pos

    Tip

    不要忘记在 constants.py 中的变量 AVAILABLE_PAIRLISTS 下注册您的 pairlist——否则它将不可选择。

    现在，让我们逐步介绍需要操作的方法：

    Pairlist 配置¶

    Pairlist Handler 链的配置在机器人配置文件的元素 "pairlists" 中完成，这是链中每个 Pairlist Handler 的配置参数数组。

    按照惯例，"number_assets" 用于指定要在 pairlist 中保留的最大交易对数量。请遵循此约定以确保一致的用户体验。

    可以根据需要配置其他参数。例如，VolumePairList 使用 "sort_key" 指定排序值——但请随意指定您的优秀算法成功和动态所需的任何内容。

    short_desc¶

    返回用于 Telegram 消息的描述。

    这应包含 Pairlist Handler 的名称，以及包含资产数量的简短描述。请遵循格式 "PairlistName - top/bottom X pairs"。

    gen_pairlist¶

    如果 Pairlist Handler 可以用作链中的主要 Pairlist Handler，定义初始 pairlist，然后由链中的所有 Pairlist Handler 处理，请覆盖此方法。示例是 StaticPairList 和 VolumePairList。

    这在机器人的每次迭代中调用（仅当 Pairlist Handler 位于第一个位置时）——因此请考虑为计算/网络密集型计算实施缓存。

    它必须返回结果 pairlist（然后可以传递给 Pairlist Handler 链）。

    验证是可选的，父类公开 verify_blacklist(pairlist) 和 _whitelist_for_active_markets(pairlist) 以执行默认过滤。如果您将结果限制为特定数量的交易对，请使用此选项——这样最终结果不会比预期的短。

    filter_pairlist¶

    此方法由 pairlist 管理器为链中的每个 Pairlist Handler 调用。

    这在机器人的每次迭代中调用——因此请考虑为计算/网络密集型计算实施缓存。

    它接收一个 pairlist（可以是先前 pairlist 的结果）以及 tickers，这是 get_tickers() 的预获取版本。

    基类中的默认实现只是为 pairlist 中的每个交易对调用 _validate_pair() 方法，但您可以覆盖它。因此，您应该在 Pairlist Handler 中实现 _validate_pair()，或者覆盖 filter_pairlist() 来执行其他操作。

    如果被覆盖，它必须返回结果 pairlist（然后可以传递给链中的下一个 Pairlist Handler）。

    验证是可选的，父类公开 verify_blacklist(pairlist) 和 _whitelist_for_active_markets(pairlist) 以执行默认过滤。如果您将结果限制为特定数量的交易对，请使用此选项——这样最终结果不会比预期的短。

    在 VolumePairList 中，这实现了不同的排序方法，进行早期验证，以便只返回预期数量的交易对。

    示例¶
        def filter_pairlist(self, pairlist: list[str], tickers: dict) -> List[str]:
        # Generate dynamic whitelist
        pairs = self._calculate_pairlist(pairlist, tickers)
        return pairs

    Protections¶

    最好阅读 Protection 文档 以了解 protections。 本指南面向想要开发新 protection 的开发人员。

    任何 protection 都不应该直接使用 datetime，而应该使用提供的 date_now 变量进行日期计算。这保留了回测 protections 的能力。

    编写新的 Protection

    最好复制现有的 Protections 之一作为好例子。

    实现新的 protection¶

    所有 Protection 实现都必须将 IProtection 作为父类。 因此，它们必须实现以下方法：

    • short_desc()
    • global_stop()
    • stop_per_pair()。

    global_stop() 和 stop_per_pair() 必须返回一个 ProtectionReturn 对象，该对象包含：

    • lock pair - 布尔值
    • lock until - datetime - 交易对应被锁定到何时（将向上舍入到下一个新蜡烛图）
    • reason - 字符串，用于日志记录和数据库存储
    • lock_side - long、short 或 '*'。

    until 部分应使用提供的 calculate_lock_end() 方法计算。

    所有 Protections 应使用 "stop_duration" / "stop_duration_candles" 来定义交易对（或所有交易对）应被锁定多长时间。 此内容作为 self._stop_duration 提供给每个 Protection。

    如果您的 protection 需要回看周期，请使用 "lookback_period" / "lockback_period_candles" 以保持所有 protections 一致。

    全局与本地停止¶

    Protections 可以有两种不同的方式来停止交易（持续有限的时间）：

    • 每个交易对（本地）
    • 所有交易对（全局）
    Protections - 每个交易对¶

    实现按交易对方法的 Protections 必须设置 has_local_stop=True。 每当交易关闭（出场订单完成）时，将调用 stop_per_pair() 方法。

    Protections - 全局保护¶

    这些 Protections 应在所有交易对上评估，因此也会锁定所有交易对的交易（称为全局 PairLock）。 全局保护必须设置 has_global_stop=True 才能评估全局停止。 每当交易关闭（出场订单完成）时，将调用 global_stop() 方法。

    Protections - 计算锁定结束时间¶

    Protections 应根据其考虑的最后一笔交易计算锁定结束时间。 这避免了如果回看期长于实际锁定期而重新锁定。

    IProtection 父类在 calculate_lock_end() 中为此提供了一个辅助方法。

    交易所止损¶

    检查新交易所是否通过其 API 支持交易所止损订单。

    由于 CCXT 尚未为交易所止损提供统一，我们需要自己实现特定于交易所的参数。最好查看 binance.py 作为此实现示例。您需要深入研究交易所的 API 文档，了解如何准确完成此操作。CCXT Issues 也可能提供很大帮助，因为其他人可能已经为他们的项目实现了类似的东西。

    不完整的蜡烛图¶

    在获取蜡烛图（OHLCV）数据时，我们可能最终得到不完整的蜡烛图（取决于交易所）。 为了演示这一点，我们将使用每日蜡烛图（"1d"）以保持简单。 我们为时间框架查询 api（ct.fetch_ohlcv()）并查看最后一个条目的日期。如果此条目更改或显示"不完整"蜡烛图的日期，那么我们应该删除它，因为不完整的蜡烛图是有问题的，因为指标假设只传递完整的蜡烛图给它们，并且会生成许多虚假的买入信号。默认情况下，我们因此移除最后一根蜡烛图，假设它是不完整的。

    要检查新交易所的行为，您可以使用以下代码片段：

    import ccxt
from datetime import datetime, timezone
from freqtrade.data.converter import ohlcv_to_dataframe
ct = ccxt.binance()  # Use the exchange you're testing
timeframe = "1d"
pair = "BTC/USDT"  # Make sure to use a pair that exists on that exchange!
raw = ct.fetch_ohlcv(pair, timeframe=timeframe)

# convert to dataframe
df1 = ohlcv_to_dataframe(raw, timeframe, pair=pair, drop_incomplete=False)

print(df1.tail(1))
print(datetime.now(timezone.utc))

                             date      open      high       low     close  volume  
499 2019-06-08 00:00:00+00:00  0.000007  0.000007  0.000007  0.000007   26264344.0  
2019-06-09 12:30:27.873327

    输出将显示交易所的最后一个条目以及当前的 UTC 日期。 如果日期显示同一天，则可以假设最后一个蜡烛图是不完整的，应该删除（保持交易所类中的设置 "ohlcv_partial_candle" 不变 / True）。否则，将 "ohlcv_partial_candle" 设置为 False 以不删除蜡烛图（如上例所示）。 另一种方法是连续多次运行此命令并观察交易量是否在变化（而日期保持不变）。

    更新 binance 缓存的杠杆层级¶

    应定期更新杠杆层级——需要启用期货的已认证账户。

    import ccxt

exchange = ccxt.binance({

# Assumes this is running in the root of the repository.

jupyter nbconvert --ClearOutputPreprocessor.enabled=True --to markdown freqtrade/templates/strategy_analysis_example.ipynb --stdout > docs/strategy_analysis_example.md

    持续集成¶

    本文档记录为 CI 管道做出的一些决定。

    • CI 在所有操作系统变体上运行，Linux (ubuntu)、macOS 和 Windows。
    • Docker 镜像为 stable 和 develop 分支构建，并构建为多架构构建，通过相同标签支持多个平台。
    • 包含 Plot 依赖项的 Docker 镜像也可作为 stable_plot 和 develop_plot 使用。
    • Docker 镜像包含一个文件，/freqtrade/freqtrade_commit，其中包含此镜像所基于的提交。
    • 完整的 docker 镜像重建每周通过计划运行一次。
    • 部署在 ubuntu 上运行。
    • 所有测试必须通过，PR 才能合并到 stable 或 develop。

    创建发布¶

    本文档的这部分面向维护者，并说明如何创建发布。

    创建发布分支¶

    Note

    确保 stable 分支是最新的！

    首先，选择一个大约一周前的提交（以不包括最新的发布添加）。

    # create new branch
git checkout -b new_release <commitid>

    确定在此提交和当前状态之间是否进行了关键错误修复，并最终挑选这些。

    • 将发布分支（stable）合并到此分支中。
    • 编辑 freqtrade/__init__.py 并添加与当前日期匹配的版本（例如，2019 年 7 月为 2019.7）。如果我们需要在该月进行第二次发布，次要版本可以是 2019.7.1。版本号必须遵循 PEP0440 允许的版本，以避免推送到 pypi 时失败。
    • 提交此部分。
    • 将该分支推送到远程并针对 stable 分支 创建 PR。
    • 将 develop 版本更新为下一个版本，遵循 2019.8-dev 模式。

    pypi¶

    手动发布

    此过程作为 Github Actions 的一部分自动化。 不应该需要手动推送到 pypi。

    手动发布

    要手动创建 pypi 发布，请运行以下命令：

    额外要求：wheel、twine（用于上传）、具有适当权限的 pypi 账户。

    pip install -U build
python -m build --sdist --wheel

# For pypi test (to check if some change to the installation did work)
twine upload --repository-url https://test.pypi.org/legacy/ dist/*

# For production:
twine upload dist/*

    请不要将非发布版本推送到生产环境 / 真实的 pypi 实例。
